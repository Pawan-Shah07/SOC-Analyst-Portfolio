# Windows Event Logs

Windows Event Logs are one of the most important sources of evidence when investigating activity on a Windows system.

Windows records a wide range of operating system, security, application, authentication, process, and system events. These records help administrators understand what happened on a system and help security analysts investigate suspicious behavior.

For a SOC analyst, Windows Event Logs provide historical evidence that can be used to answer questions such as:

```text
What happened?
When did it happen?
Which user was involved?
Which computer was affected?
What process executed?
What account changed?
Was authentication successful?
What happened before and after the event?
```

This note focuses on the structure, purpose, investigation, and practical use of Windows Event Logs.

# 1. What Are Windows Event Logs?

**Windows Event Logs** are records generated by Windows and applications to document events that occur on a system.

An event can represent:

- Successful authentication
- Failed authentication
- Process creation
- Service startup
- Service failure
- Driver activity
- Account creation
- Account modification
- Security policy changes
- Application errors
- PowerShell activity
- Network-related activity
- System startup or shutdown

Windows stores events in event logs that can be viewed locally or collected centrally.

A simplified view is:

```text
Windows System
      │
      ├── Security Events
      ├── System Events
      ├── Application Events
      ├── PowerShell Events
      └── Sysmon Events
               │
               ▼
         Event Log Files
               │
               ▼
        Event Viewer / SIEM
```

Windows Event Logs are therefore a primary source of system activity information.

---

# 2. Why Event Logs Matter to a SOC Analyst

Event logs are valuable because they provide evidence about activity occurring on endpoints.

A SOC analyst may use logs to investigate:

- Account compromise
- Brute-force attempts
- Suspicious logons
- Privilege escalation
- Malware execution
- PowerShell abuse
- Persistence
- Unauthorized account creation
- Service creation
- Suspicious process execution
- Security policy changes

For example, consider:

```text
Event ID:     4625
Account:      administrator
Source IP:    192.168.10.50
Time:         13:41:02
```

A single failed logon does not necessarily indicate an attack.

The analyst needs context:

```text
Was this the first failure?
How many failures occurred?
Was the source internal or external?
Which account was targeted?
Did a successful logon follow?
Was the source workstation authorized?
Was there other suspicious activity?
```

This is why event logs are evidence rather than conclusions.

# 3. Windows Event Log Architecture

Windows uses the **Windows Event Log service** to manage event collection, storage, and access.

The architecture includes:

```text
Applications / Windows Components
              │
              ▼
       Event Log Service
              │
              ▼
         Event Channels
              │
              ▼
        Event Log Files
              │
       ┌──────┴──────┐
       ▼             ▼
Event Viewer        SIEM
```

### Event sources

Events can be generated by:

- Windows operating system components
- Security components
- Applications
- Services
- Drivers
- PowerShell
- Sysmon
- Third-party software

### Channels

Windows uses **event channels** to organize events.

Examples:

```text
Security
System
Application
Windows PowerShell
Microsoft-Windows-PowerShell/Operational
Microsoft-Windows-Sysmon/Operational
```

### Event log files

Traditional Windows event logs are stored as `.evtx` files.

Common locations include:

```text
C:\Windows\System32\winevt\Logs\
```

Examples:

```text
Security.evtx
System.evtx
Application.evtx
```

# 5. Security Log

The **Security** log contains events related to Windows security activity.

It is one of the most important Windows logs for security investigations.

The Security log can contain events related to:

- Logon attempts
- Logoffs
- Account management
- Group membership changes
- Privilege use
- Security policy changes
- Object access, when auditing is configured

| 4625 | Failed logon |
| 4634 | Logoff |
| 4647 | User-initiated logoff |

| 4688 | New process created |
| 4697 | Service installed |
| 4720 | User account created |
| 4722 | User account enabled |
| 4723 | Attempt to change password |
| 4724 | Attempt to reset password |
| 4725 | User account disabled |
| 4726 | User account deleted |

# 6. System Log

The **System** log records events generated by Windows system components.

Typical event sources include:

- Drivers
- Services
- Hardware
- Operating system components
- Service Control Manager
- Kernel-related components

Examples of information that can appear include:

- Service startup
- Service failure
- Driver problems
- Unexpected shutdown
- System startup
- Hardware-related problems

### Example

```text
Event Source:
Service Control Manager

Event:
A service entered the running state.
```

A System log investigation may help determine whether:

- A service was unexpectedly started
- A critical service stopped
- A driver failed
- A system reboot occurred
- A recurring system problem exists

---

# 7. Application Log

The **Application** log contains events generated by applications.

Examples include:

- Application crashes
- Runtime errors
- Application warnings
- Database errors
- Service-specific events
- Software installation or operational messages

Example:

```text
Source:
Application Error

Event:
A program terminated unexpectedly.
```

The Application log is particularly useful when investigating:

- Crashes
- Application instability
- Suspicious software behavior
- Service failures
- Errors associated with a particular application

The Application log is generally less security-focused than the Security log, but it can provide important supporting evidence.

# 8. Windows PowerShell Logs

PowerShell is a legitimate administrative tool that can also be abused by attackers.

Windows can generate several PowerShell-related logs and events.

Important channels include:

```text
Windows PowerShell
Microsoft-Windows-PowerShell/Operational
```

### Important PowerShell Event IDs

#### Event ID 400

Indicates that the PowerShell engine started.

#### Event ID 403

Indicates that the PowerShell engine stopped.

#### Event ID 600

Relates to PowerShell provider lifecycle activity in Windows PowerShell logging.

#### Event ID 4103

**Module Logging** can record pipeline execution details for PowerShell modules.

#### Event ID 4104

**Script Block Logging** records PowerShell script block content when enabled.

Example:

```text
Event ID: 4104
PowerShell Script Block:
Get-Process
Get-Service
```

The usefulness of PowerShell logs depends heavily on audit and logging configuration.

### Why PowerShell logs are valuable

They can help identify:

- Script execution
- Suspicious commands
- Encoded commands
- Download activity
- Reconnaissance
- Persistence commands
- Administrative changes

Example suspicious pattern:

```powershell
powershell.exe -EncodedCommand <encoded-content>
```

An analyst should investigate the complete event and surrounding context rather than treating every encoded PowerShell command as malicious.

# 9. Microsoft-Windows-Sysmon/Operational

**Sysmon (System Monitor)** is a Microsoft Sysinternals tool that provides detailed telemetry about system activity.

Sysmon writes its events to:

```text
Microsoft-Windows-Sysmon/Operational
```

Sysmon provides telemetry that is often more detailed than the default Windows event logs.

### Important Sysmon Event IDs

| Event ID | Description |
|---:|---|
| 1 | Process creation |
| 2 | File creation time changed |
| 3 | Network connection |
| 4 | Sysmon service state changed |
| 5 | Process terminated |
| 6 | Driver loaded |
| 7 | Image loaded |
| 8 | CreateRemoteThread |
| 10 | Process access |
| 11 | File created |
| 12 | Registry object added/deleted |
| 13 | Registry value set |
| 14 | Registry object renamed |
| 15 | Alternate data stream created |
| 17 | Named pipe created |
| 18 | Named pipe connected |
| 22 | DNS query |
| 23 | File deleted |
| 25 | Process tampering |

Sysmon event availability can depend on the installed Sysmon version and configuration.

### Example Sysmon Event ID 1

```text
Event ID: 1
Image: C:\Windows\System32\cmd.exe
ParentImage: C:\Windows\explorer.exe
CommandLine: cmd.exe /c whoami

```

This provides significantly more context than a simple process-name entry.

### Sysmon's value

Sysmon can provide telemetry for:

- Process execution
- Parent-child relationships
- Network connections
- DNS queries
- Registry changes
- File creation
- Process access
- Driver loading
- Process tampering

Sysmon should be treated as a telemetry source that requires appropriate configuration and analysis.

# 10. Event Log Structure

A Windows event is structured data containing information about the event.

A simplified event structure looks like:

```text
Event
│
├── System
│   ├── Provider
│   ├── Event ID
│   ├── Version
│   ├── Level
│   ├── Task
│   ├── Opcode
│   ├── Keywords
│   ├── TimeCreated
│   ├── EventRecordID
│   ├── Correlation
│   ├── Execution
│   ├── Channel
│   ├── Computer
│   └── Security
│
└── EventData
    ├── User
    ├── Process
    ├── IP Address
    ├── Logon Type
    └── Additional data
```

Not every event contains every field.

The exact fields depend on the provider and event type.

---

# 11. Important Event Fields

A SOC analyst should become comfortable identifying important fields.

## Provider

Identifies the component that generated the event.

Example:

```text
Microsoft-Windows-Security-Auditing
```

or:

```text
Microsoft-Windows-Sysmon
```

---

## Event ID

Identifies the specific event definition.

Example:

```text
4624
```

means successful logon in the standard Windows Security auditing event set.

---

## Level

Indicates the general event severity level provided by the event source.

Common levels include:

- Critical
- Error
- Warning
- Information
- Verbose

Severity must always be interpreted in context. A "Warning" is not automatically a security incident.

---

## TimeCreated

The timestamp associated with the event.

Example:

```text
2026-08-18 13:41:02
```

Time correlation is essential when building an investigation timeline.

---

## Computer

Identifies the system that generated the event.

Example:

```text
WIN10-CLIENT01
```

---

## User / Account

Identifies the user associated with the event, when applicable.

Example:

```text
DOMAIN\jsmith
```

---

## Process ID

Identifies the process associated with an event, when available.

Example:

```text
PID: 4820
```

A PID can be useful when correlating related process activity.

---

## Process Name / Image

Identifies the executable involved.

Example:

```text
C:\Windows\System32\powershell.exe
```

---

## Command Line

Shows how a process was launched, when available.

Example:

```text
powershell.exe -ExecutionPolicy Bypass -File script.ps1
```

Command-line information can provide much more context than the process name alone.

---

## Source Network Address

Some events contain network information such as:

```text
Source IP:
192.168.10.50
```

This can help identify where an authentication or network-related action originated.

---

## Logon Type

Authentication events such as Event ID 4624 contain a **Logon Type**.

Common examples include:

| Logon Type | Meaning |
|---:|---|
| 2 | Interactive |
| 3 | Network |
| 4 | Batch |
| 5 | Service |
| 7 | Unlock |
| 8 | NetworkCleartext |
| 9 | NewCredentials |
| 10 | RemoteInteractive |
| 11 | CachedInteractive |

These values are important when determining how a user or process accessed a system.

---

# 12. Event IDs vs Event Types

These terms should not be confused.

## Event ID

An **Event ID** identifies a particular event definition.

Example:

```text
4624
```

can represent a successful logon in the Windows Security event set.

## Event Type / Event Level

A log can also describe the nature or severity of an event.

Common levels include:

```text
Information
Warning
Error
Critical
Verbose
```

Therefore:

```text
Event ID = What specific event is this?
Level    = What general type/severity does the provider assign?
```

A high-severity event is not automatically malicious, and a normal informational event can still be useful during an investigation.

# 13. Authentication Events

Authentication events are among the most important Windows events for security investigations.

They can help answer:

```text
Who authenticated?
When?
From where?
How?
Was the authentication successful?
What account was targeted?
```

### Event ID 4624 — Successful Logon

Indicates a successful logon.

Example:

```text
Event ID: 4624
Account: DOMAIN\john
Logon Type: 10
Source IP: 192.168.10.25
```

This may represent a successful Remote Desktop logon when Logon Type 10 is used.

---

### Event ID 4625 — Failed Logon

Indicates a failed logon attempt.

Example:

```text
Event ID: 4625
Target Account: administrator
Source IP: 192.168.10.40
Failure Reason: Unknown user name or bad password
```

A single failure may be normal.

Repeated failures from one source can indicate:

- Mistyped password
- Misconfigured application
- Forgotten credentials
- Brute-force activity
- Password spraying

Context is essential.

---

### Event ID 4648 — Explicit Credentials

This event can indicate that a process attempted a logon using explicitly supplied credentials.

It can be important during investigations involving:

- Credential misuse
- Administrative activity
- Lateral movement
- Scheduled tasks
- Service execution

---

### Event ID 4740 — Account Locked Out

Indicates that an account was locked.

Repeated account lockouts may indicate:

- User error
- Old stored credentials
- Misconfigured services
- Password spraying
- Brute-force attempts

---

### Kerberos Events

In domain environments, important events include:

```text
4768 → TGT request
4769 → Service ticket request
4771 → Kerberos pre-authentication failure
```

These can be useful for investigating authentication behavior within Active Directory environments.

# 14. Process and Program Execution

Understanding what executes on a Windows endpoint is fundamental to endpoint investigation.

## Event ID 4688

Windows Security auditing can generate **Event ID 4688** when a new process is created, assuming the relevant audit policy is enabled.

Example:

```text
Event ID: 4688
New Process:
C:\Windows\System32\cmd.exe

Creator Process:
C:\Windows\explorer.exe

Command Line:
cmd.exe /c whoami
```

This can help answer:

```text
What executed?
Who launched it?
What was the parent process?
What command line was used?
When did it execute?
```

---

## Sysmon Event ID 1

Sysmon Event ID 1 provides detailed process creation telemetry.

Example:

```text
Image:
C:\Windows\System32\powershell.exe

Parent Image:
C:\Windows\explorer.exe

Command Line:
powershell.exe -File C:\Users\Public\script.ps1
```

This parent-child relationship can reveal suspicious execution chains.

Example:

```text
winword.exe
      │
      └── powershell.exe
              │
              └── cmd.exe
```

Such a chain should be investigated in context because office applications can legitimately launch scripts or child processes in some environments.

# 17. Useful PowerShell Commands

PowerShell provides several methods for querying Windows event logs.

## Get-WinEvent

The most flexible modern command is:

```powershell
Get-WinEvent
```

List recent Security events:

```powershell
Get-WinEvent -LogName Security -MaxEvents 20
```

List recent System events:

```powershell
Get-WinEvent -LogName System -MaxEvents 20
```

List recent Application events:

```powershell
Get-WinEvent -LogName Application -MaxEvents 20
```

---

## Filter by Event ID

Example:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    Id = 4625
} -MaxEvents 20
```

This returns recent failed logon events.

---

## Filter by Time

Example:

```powershell
$start = (Get-Date).AddHours(-1)

Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    StartTime = $start
}
```

---

## Filter by Multiple Event IDs

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    Id = 4624,4625,4648,4740
}
```

---

## PowerShell Operational Log

```powershell
Get-WinEvent -LogName 'Microsoft-Windows-PowerShell/Operational' -MaxEvents 20
```

---

## Sysmon Log

```powershell
Get-WinEvent -LogName 'Microsoft-Windows-Sysmon/Operational' -MaxEvents 20
```

---

## View Available Logs

```powershell
Get-WinEvent -ListLog *
```

This can return a large amount of information.

To find PowerShell-related logs:

```powershell
Get-WinEvent -ListLog * | Where-Object LogName -like '*PowerShell*'
```

---

## Select Specific Fields

Example:

```powershell
Get-WinEvent -FilterHashtable @{
    LogName = 'Security'
    Id = 4625
} -MaxEvents 10 |
Select-Object TimeCreated, Id, ProviderName, Message
```

This produces a more focused output.

# 18. Example SOC Investigation

Consider the following scenario.

A Windows workstation generates several failed logon events.

### Initial Alert

```text
Event ID: 4625
Account: administrator
Source IP: 192.168.10.50
```

The first step is not to immediately declare an attack.

---

## Step 1 — Count the failures

Suppose the analyst discovers:

```text
13:20 → 4625
13:21 → 4625
13:21 → 4625
13:22 → 4625
13:22 → 4625
...
```

There are many failures in a short time.

This is more suspicious than a single failed login.

---

## Step 2 — Identify the source

The source IP is:

```text
192.168.10.50
```

The analyst determines that this belongs to:

```text
UNKNOWN-WORKSTATION
```

This increases concern.

---

## Step 3 — Check for successful authentication

Search for:

```text
4624
```

from the same source.

Suppose the analyst finds:

```text
13:24 → 4624
Account: administrator
Source IP: 192.168.10.50
```

Now the investigation becomes more important.

---

## Step 4 — Inspect the logon type

Suppose the successful event contains:

```text
Logon Type: 10
```

This indicates RemoteInteractive logon, commonly associated with Remote Desktop.

---

## Step 5 — Investigate process activity

Search Sysmon process creation events around the same timestamp.

Suppose:

```text
13:25:03
powershell.exe
```

was launched.

The command line is:

```text
powershell.exe -ExecutionPolicy Bypass -File C:\Users\Public\update.ps1
```

This requires further investigation.

---

## Step 6 — Build a timeline

```text
13:20
Failed logon attempts begin

13:22
Repeated failed logons

13:24
Successful administrator logon

13:25
PowerShell executes

13:26
Additional activity observed
```

The timeline is more informative than any single event.

---

## Step 7 — Determine the verdict

The analyst considers:

```text
Was the administrator account expected?
Was Remote Desktop authorized?
Who owns the source workstation?
Was the PowerShell script legitimate?
What does update.ps1 contain?
Were additional accounts created?
Were network connections established?
```

The final verdict might be:

```text
True Positive
```

or:

```text
Benign / Authorized Administrative Activity
```

depending on the evidence.

# 20. Common Challenges

## Challenge 1 — Too Many Events

Windows systems generate large amounts of telemetry.

Solution:

Use focused filters:

```text
Log
+
Event ID
+
Time Range
+
Host
+
User
```

---

## Challenge 2 — Event ID Alone Is Not Enough

An Event ID provides a starting point, not a complete conclusion.

For example:

```text
4624 = successful logon
```

A successful logon is not inherently malicious.

Always examine:

- Account
- Logon type
- Source
- Time
- Destination host
- Context

---

## Challenge 3 — Audit Policy Not Enabled

Some useful security events depend on appropriate audit configuration.

If auditing is not enabled, the required event may not exist.

Therefore:

> No event does not necessarily mean no activity occurred.

---

## Challenge 4 — Log Overwrite

Event logs have configured sizes and retention behavior.

Older events can eventually be overwritten depending on configuration.

This can create gaps in historical evidence.

---

## Challenge 5 — Time Synchronization

Incorrect system clocks make correlation difficult.

For investigations involving multiple systems, timestamps should be interpreted with awareness of:

- Time zone
- UTC/local time
- Clock drift
- NTP configuration

---

## Challenge 6 — Multiple Similar Events

A single action can generate events in multiple logs.

For example:

```text
User Logon
   │
   ├── Security
   ├── Sysmon
   ├── PowerShell
   └── Application
```

Correlation across logs can provide much more context.

---

## Challenge 7 — Legitimate Administrative Activity

Administrators may legitimately use:

```text
PowerShell
cmd.exe
RDP
services.exe
scheduled tasks
remote management
```

Therefore:

> Suspicious-looking tools are not automatically malicious.

The analyst must evaluate context, user, timing, command line, parent process, destination, and business justification.

# 21. SOC Analyst Checklist

Use this checklist whenever investigating Windows Event Logs.

### Initial Event

- [ ] Identify the event ID.
- [ ] Identify the event source/provider.
- [ ] Record the timestamp.
- [ ] Identify the affected computer.
- [ ] Identify the associated user/account.
- [ ] Read the complete event message.

### Authentication

- [ ] Determine whether authentication succeeded or failed.
- [ ] Identify the logon type.
- [ ] Identify the source IP or workstation.
- [ ] Check for repeated failures.
- [ ] Check for successful authentication after failures.
- [ ] Check for account lockout events.

### Process Activity

- [ ] Identify the process.
- [ ] Identify the parent process.
- [ ] Review the command line.
- [ ] Check the user context.
- [ ] Review Sysmon Event ID 1 when available.
- [ ] Investigate unusual parent-child relationships.

### PowerShell

- [ ] Check PowerShell logs.
- [ ] Review Event ID 4103 when available.
- [ ] Review Event ID 4104 when Script Block Logging is enabled.
- [ ] Look for encoded commands.
- [ ] Look for download or execution behavior.
- [ ] Validate whether the activity is authorized.

### Account Changes

- [ ] Check for new accounts.
- [ ] Check account enable/disable events.
- [ ] Check password changes/resets.
- [ ] Check group membership changes.
- [ ] Check for privilege changes.

### Correlation

- [ ] Search related events before the alert.
- [ ] Search related events after the alert.
- [ ] Check System logs.
- [ ] Check Application logs.
- [ ] Check PowerShell logs.
- [ ] Check Sysmon logs.
- [ ] Check network telemetry when available.

### Investigation

- [ ] Build a timeline.
- [ ] Determine affected systems.
- [ ] Determine affected accounts.
- [ ] Determine source and destination.
- [ ] Determine whether the behavior is expected.
- [ ] Determine whether the event is benign, suspicious, or malicious.

### Documentation

- [ ] Record evidence.
- [ ] Record event IDs.
- [ ] Record timestamps.
- [ ] Record affected hosts.
- [ ] Record accounts.
- [ ] Record source IPs.
- [ ] Record process names and command lines.
- [ ] Record the final verdict.
- [ ] Document recommended response actions.

# Final Mental Model

When reading a Windows event, think:

```text
WHO?
│
├── User
└── Process

WHAT?
│
├── Event ID
├── Action
├── Process
└── Command Line

WHEN?
│
└── Timestamp

WHERE?
│
├── Computer
└── Source IP

HOW?
│
├── Logon Type
├── Parent Process
└── Authentication Method

WHAT NEXT?
│
├── Related Events
├── Network Activity
├── Persistence
└── Account Changes
```

A Windows Event Log should rarely be investigated in isolation.

The strongest investigations correlate:

```text
Security
   +
System
   +
Application
   +
PowerShell
   +
Sysmon
   +
Network Telemetry
```

This combination allows an analyst to reconstruct what happened on a Windows endpoint with much greater confidence.

# Key Takeaways

1. Windows Event Logs provide historical records of system and application activity.
2. The Security log is one of the most important sources for security investigations.
3. System and Application logs provide important supporting context.
4. PowerShell logging can provide valuable command and script information.
5. Sysmon provides detailed endpoint telemetry when properly configured.
6. Event IDs identify specific event definitions.
7. Event fields provide the context required to interpret an event.
8. Authentication events such as `4624`, `4625`, and `4740` are important for account investigations.
9. Process creation events such as `4688` and Sysmon `1` help identify program execution.
10. Account-management events help identify unauthorized account and privilege changes.
11. Event Viewer provides a graphical method for examining logs.
12. `Get-WinEvent` is a powerful PowerShell tool for querying Windows events.
13. Event ID alone is not enough to determine whether an event is malicious.
14. Time, user, host, source, process, command line, and related events provide essential context.
15. Event-log investigations should follow a structured workflow.
16. Correlation across multiple log sources is more powerful than examining a single event.
17. Missing logs do not necessarily mean that activity did not occur.
18. Logging configuration, retention, and time synchronization directly affect investigation quality.
19. Legitimate administrative tools can be abused, so behavior must be assessed in context.
20. A good SOC analyst turns individual events into a **timeline and evidence-based conclusion**.
